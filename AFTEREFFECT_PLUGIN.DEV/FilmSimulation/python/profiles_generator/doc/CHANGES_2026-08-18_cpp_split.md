# C++ database split + explicit initialisation — 2026-08-18

Owner-approved redesign of the generated C++ ("Option C" + explicit-init API).
Investigation record is in the conversation of 2026-08-18; this file is the
durable summary.

## The problem, measured

`film_profiles.cpp` was 676 KB, of which **656 KB (97 %) was ONE function** —
`GetFilmDatabase()` returning a `std::vector<FilmProfile>` from a single
braced-init-list of 155 elements (11,231 braces, ~30,000 numeric literals,
4,689 strings). `FilmProfile` owns `std::string`/`std::vector` members, so
that list is constructor code, not data — plus an `initializer_list` backing
array of 155 full temporaries on the stack, plus a deep COPY of every element
(`initializer_list` is const; a vector cannot move from it). MSVC 2015's
limits (C1060/C1026, optimiser blow-up) are per-FUNCTION; the owner's
VS2015 SP3 + ICC environment could not compile it reliably.

Measured here (g++ 13, same source): the reconstructed monolith takes
**18.9 s** for the one TU; the new worst slot takes **0.6 s**. (Peak-memory
comparison was inconclusive in this sandbox — the sampler caught the compiler
driver, not cc1plus — so no memory number is quoted.)

## The new shape (all generated by cpp_codegen.py)

| File | Role |
|---|---|
| `film_profiles_data_01..16.cpp` | consecutive, size-balanced slices (39–45 KB each); one `v.push_back(FilmProfile{...})` per profile — statement-per-profile bounds function size, and rvalue push_back MOVES instead of copying |
| `film_profiles_detail.hpp` | internal: declares the 16 append functions |
| `LoadFilmDataBase.h/.cpp` | the explicit-init API (below) |
| `film_profiles.cpp` | now 21 KB: print stocks + formats as first-call function-local statics |
| `film_profiles.hpp` | signature change: the three accessors return **const&** (owner decision) |
| `film_enum.hpp`, `film_names.txt` | **unchanged in format, order and bytes** — film_names.txt regenerated byte-identical (MD5 `ae9e4be3…`) |

The slot count is FIXED at 16 and every slot file is always emitted (empty
slots as a no-op), so the owner's `.vcxproj` lists the files once and never
changes as the database grows. If the DB outgrows the slots, generation FAILS
LOUDLY (per-slot 112 KB source limit) instructing to raise `N_DATA_SLOTS` and
add the file to the project — a deliberate manual step.

## The initialisation model (owner-specified, validated)

* **Nothing at DLL load.** No namespace-scope dynamic initialiser does work:
  storage is a function-local static, the flags are constant-initialised.
* **`bool film::LoadFilmDataBase(void)`** — called from the effect's
  GlobalSetup. Builds all 155 profiles exactly once (`std::call_once`;
  concurrent GlobalSetup safe), single `reserve()` so the element array is
  one allocation, count-checked against `eTOTAL_FILMS_PROFILES`, pre-warms
  the print-stock and format tables. Returns success/failure; a FAILED load
  (bad_alloc) does **not** latch — a later call retries.
* **`const FilmProfile* film::GetFilmProfile(eFILM_PROFILE)`** — the render
  API: O(1) index, no lock, no allocation, `noexcept`, `nullptr` on
  not-loaded/out-of-range. Matches the engine, which passes
  `const film::FilmProfile&` into its stages.
* **`GetFilmDatabase()` now returns `const std::vector<FilmProfile>&`**
  (owner asked "why not const reference?" — agreed: the table is immutable
  after build, so by-value forced a pointless deep copy per call).
  Source-compatible with every existing call site checked:
  `AlgoMemHandler.cpp`'s `static const std::vector<...> table = ...;`
  copy-initialises exactly as before; `test_filmcoord.cpp` binds read-only.
  OPTIONAL follow-up for the owner: change those three engine statics to
  `static const auto& table = ...;` to drop the duplicate copies entirely.
* **Deliberately NO Unload API**: `GetFilmProfile` hands out raw pointers
  into storage; an unload would be a dangling-pointer factory.
* Full static allocation was evaluated and is impossible with the current
  schema (`std::string`/`std::vector` members allocate by nature); the POD
  mirror-schema alternative is recorded as a future option, not taken.
* Requires `/Zc:threadSafeInit` (VS2015 default) — do not disable magic
  statics.

## Verified

* All 18 generated TUs: `g++ -std=c++14 -Wall -Wextra`, exit 0 AND zero bytes.
* Runtime test TU: refuses access before load; 8 threads racing
  `LoadFilmDataBase()` all succeed; per-profile lookup, bounds, legacy
  copy-init, reference identity, and **enum value == vector index for all
  155 entries**; 155/9/14 profiles/prints/formats.
* `film_names.txt` byte-identical before/after; separator law and order
  re-asserted; deterministic regeneration (stamp-stripped content identical
  across runs).
* `build.py`: GENERATED set now 23 files; compile stage gates every TU.
